# Camera WebRTC live contract

This optional iOS-first capability is isolated from ordinary Studio controls. A generated page may expose live video only when the public device definition returns both the exact `WebRTCProvideOffer` command (`AqaraSpecCid=40336`) and `WebRTCSignalingEvent` trait (`AqaraSpecTid=20778`). Exact `WebRTCProvideICECandidates` (`AqaraSpecCid=40338`) enables Trickle ICE; `WebRTCEndSession` (`AqaraSpecCid=40339`) is used when returned. Names, models and the camera category never synthesize streaming capability.

The H5 calls only the capability-advertised native methods `cameraWebRTCPrepareLive`, `cameraWebRTCCreateSession`, `cameraWebRTCAddIceCandidate`, and `cameraWebRTCCloseSession`, and consumes `onCameraWebRTCSignal`. Android and older iOS hosts do not advertise the complete transport and must degrade to an unavailable live-view control or use the explicit complete-Offer compatibility mode without issuing 40338.

`prepare` revalidates the current Studio definition, starts the host signaling transport, registers a scoped device signaling interest, waits for its subscription ACK, and invokes the authenticated `getIceServers` operation immediately before creating the PeerConnection. The documented server path is `POST /api/v1/webrtc/ice-servers`; Life's Studio transport may expose the equivalent routed path `/open/api/v1/webrtc/ice-servers`. Send the V1 envelope `type=GetIceServersRequest`, `version=v1`, and a fresh `msgId`, then require `code=0`, an object `data`, and an array `data.iceServers`. Accept both the LAN versioned envelope and the authenticated cloud `code/data/message` envelope. Response `type`, `version`, and `msgId` may be absent; when present, require `type=GetIceServersResponse`, `version=v1`, and a non-empty `msgId`. Missing optional metadata must not discard otherwise valid TURN servers. Bind the result to the current authenticated request and Studio context. Treat an exact response/request `msgId` match as preferred correlation, but remain compatible with deployed authenticated services that assign a distinct response ID; never use an ID mismatch to accept data from another request or context. An empty array is valid LAN-only configuration. Accept only bounded `stun:`, `stuns:`, `turn:` or `turns:` URL arrays; TURN entries require both username and credential. Return a short-lived, device-bound ticket plus that native-provided configuration. Never emit the request/response body, URLs, usernames or credentials through the generic HTTP trace logger, and never persist or reuse the response across attempts.

Store the exact configuration only with the current in-memory ticket. If the ICE service fails, a host may return an empty server list with an explicit unavailable status so LAN host candidates can still be tried; remote success then remains unverified and the UI must expose that status on failure. `create` accepts live mode only, a distinct random `requestId` of at most 32 UTF-8 bytes, a bounded SDP offer, and the ticket. Native—not H5—is authoritative for the ICE servers and browser transport policy; H5-provided ICE values must not redirect the camera. The device Offer includes ICE servers only when available and does not inherit the browser-only transport policy. Keep standard `urls`/`username`/`credential` objects for the PeerConnection, but encode Offer field 4 as Aqara Spec `ICEServerStructure` members `URLs(0)`/`Username(1)`/`Credential(2)`/`CredentialType(3="0")`, capped at 10 servers. Native sends one structured Offer command with `StreamUsage=0x03`; it never adds this command to `safeCommandCodes`. The device-assigned Answer must contain SDP and a valid uint16 `SessionId`.

When the same fresh definition exposes valid 40338 fields and native advertises `cameraWebRTCAddIceCandidate`, use true Trickle ICE. Register the local `icecandidate` observer before `setLocalDescription`, send the Offer without waiting for gathering to complete, queue candidates until the Answer has been applied and its uint16 SessionId is active, then forward them sequentially. Native rechecks ticket, device and active SessionId and emits 40338 with `SessionId(0)` and `ICECandidates(1)`; each candidate structure contains exact `Candidate(0)`, `SDPMid(1)` and `SDPMLineIndex(2)`. Bound candidate and mid lengths, never log them, isolate an individual send failure, and retain the 30-second state-aware connection deadline. When 40338 or the native method is absent, wait for gathering and send one complete Offer; never mix both modes in one attempt.

For a new session, include the defined Offer `SessionId` field with an explicit null value; never invent an ID from `requestId`. Encode `InitiatorData` as a JSON string containing a bounded `correlationToken`, using the random request ID as its value. Include `SDP`, `StreamUsage=3`, and available `ICEServers`; do not append `ICETransportPolicy` to the device command unless the device protocol explicitly requires it. This command shape is part of the camera protocol, independent of any particular application repository. Use a command operation that returns the device report, validate its success status and uint16 `SessionId`, and bind all subsequent Answer, ICE and End events to that ID. If the host transport cannot return that report, fail with a distinct signaling error rather than accepting the first Answer observed on a shared subscription.

Subscribe before Offer. During the one pending Offer, deduplicate the full signaling payload, listen for WebSocket reports, and perform a one-second targeted trait read only until Answer or the 30-second timeout. Buffer signals that arrive before the command report and deliver only those matching its device `SessionId`. Deliver valid ICE candidates carried in the Answer event as well as later ICE events; retain early ICE by session until the browser listener is ready. On cancellation, close a valid late-arriving device session. Never log SDP, ICE candidates, credentials or authorization data.

Coalesce repeated start activation for the same camera while its attempt is pending, and never let completion from an older attempt mutate the current card state. Native subscription ACK handling is revision-aware: only the newest subscription revision for the isolated camera owner may resolve or reject `prepare`; an older `subscriptionSuperseded` callback is stale and must not fail the active attempt.

Create one PeerConnection per user attempt. When native returns ICE servers, construct that connection once with the complete native configuration and the returned policy; `all` gathers host and relay candidates together, so do not first wait for a separate empty/direct profile. With no returned servers, use an empty list and `all` for LAN-only operation. Keep the browser's original local description intact, but remove nonnumeric mDNS candidates from the device-facing Offer and local Trickle ICE because the camera protocol cannot resolve those addresses. For a complete Offer, remove the `trickle` ICE option from the signaling copy after gathering. `relay` is an explicit diagnostic or product policy, not an automatic retry. Never embed TURN credentials in H5, generated config, skill assets, fixtures shipped as production, storage, analytics or logs, and never invent a public server. A connection is successful only after the video element has current data or inbound video RTP bytes. After the Answer is applied, use a 30-second state-aware media deadline: fail immediately on PeerConnection or ICE `failed`/`closed`, continue through `new`/`checking`/`connecting` and transient `disconnected`, report an ICE timeout when connectivity never completes, and report a media-readiness timeout when ICE/PeerConnection connected but no video frame or inbound video RTP arrived. Failure releases the PeerConnection, tracks, timers, observers, native subscription owner and any valid device session before UI error; retry is user-initiated and obtains a fresh ticket/configuration.

Production native code obtains short-lived TURN credentials from the authenticated service, validates `stun:`, `turn:` or `turns:` URLs, bounds the server list, and returns only the current ticket's configuration. Do not retain hardcoded test relays in app source, Builder assets, generated H5, storage, analytics, captured logs or committed QA fixtures. Prefer a service response containing UDP TURN plus TCP/TLS fallbacks where supported. Before release, verify credential expiry, server-clock behavior, redaction, LAN host selection under `all`, remote relay selection, and failure after invalid/expired credentials.

Before applying the device Answer in iOS WKWebView, normalize every line ending to CRLF with a trailing CRLF. Extract media-section `a=candidate:` lines, call `setRemoteDescription` with the candidate-free SDP, then add the extracted candidates individually with their returned `mid` and media index. Preserve candidate text exactly, isolate a rejected candidate without dropping later candidates, and register the native trickle-ICE observer afterward. This is a WebKit compatibility normalization only; it must not invent, rewrite or persist signaling data.

The page allows at most one active camera session. Pause/continue uses media-element pause/play and retains the established session; page hide, background, collection replacement and explicit close release it. Remote End updates only that camera card. Live controls do not rebuild the device grid or change card occupancy.

The card uses the profile's largest existing device-card occupancy, local relative assets, `playsinline`, and theme tokens. An offline camera must show explicit offline status and a disabled neutral “offline” action; it must not retain an enabled-looking or misleading “start live view” action. Host-unavailable and cached states remain distinct from device offline. Fixture signaling belongs only in QA. Real completion requires an iOS build plus a physical camera/Studio session; static and simulated tests cannot prove media traversal.

## Video presentation

Reserve a responsive `aspect-ratio:16/9` viewport before media arrives. Position the video within that viewport at `width:100%;height:100%;object-fit:contain;object-position:center`. Preserve the source aspect ratio and show neutral letterboxing for 4:3 or portrait sources; never stretch, crop with `cover`, or use a fixed pixel video height. The card may grow with viewport width, but connecting, pausing and source-resolution changes must not alter its geometry. Keep this CSS presentation independent of session creation, SDP/ICE, tracks, playback and bridge code. Verify camera/control containment and neighboring-card separation at narrow and wide widths, and verify landscape and portrait media using QA-only local canvas streams. Run `scripts/profile_camera_layout.mjs <output> --playwright-module <available-module> --browser <available-chromium>`. No QA media, screenshots or diagnostics belong in the production package.
