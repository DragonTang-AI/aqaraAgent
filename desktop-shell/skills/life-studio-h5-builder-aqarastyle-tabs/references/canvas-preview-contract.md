# PC canvas preview and App export

This is an optional generation mode of the independently distributable tabs skill. It does not change production templates, require App source changes, depend on a particular agent/canvas implementation, or prove real Studio/device behavior.

## Commands and editing loop

Generate with `node scripts/generate_h5.mjs --output <new-workspace> --title 我的家 --tabs home,devices,automation --with-preview`. Omit `--with-preview` to preserve the existing flat H5 output. All four tab selections remain supported.

The workspace contains `runtime/`, `preview/`, `manifest.json`, and `README.txt`. Runtime contains the existing 16 production HTML/JS/CSS files plus the optional `server.py` helper. Preview contains a derived `index.html`, an optional standalone `canvas.html`/`canvas.js` wrapper, `preview-bootstrap.js`, `preview-host.js`, `mock-studio.js`, `preview.css`, `sample-camera.svg`, and the three scenario JSON files. Current-position and StopMotion fixtures support the Space control preview. `scenarios.js` and `settings.js` are derived data/initialization assets, not separately maintained sources. The manifest records relative entry paths, protocol version, fixture-contract version, and runtime/preview SHA-256 inventories. Its revision changes when either production or preview content changes. `life-studio-preview-v1` names this skill's maintained fixture contract, not an official Studio API version.

For changes, edit the production source under `runtime/` and optionally preview scenario JSON. Never edit the derived preview HTML, settings or scenario JavaScript as a second UI. Run `node scripts/refresh_preview.mjs <workspace>` to regenerate those files and hashes; it preserves preview host files and customized scenario JSON. Run `validate_preview.mjs` and `smoke_preview.mjs` with existing Node.js; run `profile_preview.mjs` only with an existing Playwright Node module/browser. Follow SKILL.md’s no-automatic-installation rule: never install pip/npm packages or browsers for verification. If browser prerequisites are unavailable, use existing platform canvas/browser tools where possible and report the scripted browser gate as not run. Also run the existing runtime validators/smokes and relevant UI gates against `<workspace>/runtime`. Place QA output outside the complete workspace, never inside either subtree. Produce no screenshots/logs/reports in delivery directories.

Export with `node scripts/export_app.mjs <workspace> <new-app-directory>`. It verifies workspace integrity, fixture identity, derived-page parity, and runtime validation before copying the 16 production files plus explicitly inventoried local media/font assets under runtime/assets/. The exported flat directory loads `index.html` in Aqara Life and passes `validate_h5.mjs` without `server.py`. The optional local server, manifest, preview code/data, sample camera asset and QA records are excluded. Optional runtime/assets/ supports local images, fonts and MP4/WebM media. Executable files, symlinks, preview/QA names and active/external SVG content are rejected; every exported asset is hashed. Additional production scripts require an explicit contract update, never arbitrary directory copying.

## Hosting / iframe integration

Serve the entire workspace over HTTP(S) on a dedicated preview origin. Open `preview/canvas.html` for the provided PC wrapper, or embed `preview/index.html` directly. The iframe sandbox is `allow-scripts allow-same-origin`; do not embed the preview on the sensitive main-site origin. That combination is an execution/storage boundary only when origins are separated, not a substitute for origin isolation. The bundled wrapper assumes it is hosted on the same dedicated preview origin as its iframe.

The derived page references runtime assets through `base href="../runtime/"`. Bootstrap installs a simulated native-message transport first, then sequentially loads the original production script list, including unmodified `life-bridge.js`. No alternate domain mapping or rendering pipeline is created. Initialization refuses existing native-host context/bridges before starting production scripts. There is no Mock query switch or unavailable-bridge fallback in the production entry.

Preview CSP denies network connections, external scripts/media, objects and forms. It permits only same-origin assets and required inline CSS. Do not loosen this policy to fetch Studio data. All fixture data loads as local scripts before runtime startup; no network-backed Mock service is required. Preview uses in-memory writes and replaces sessionStorage with per-iframe volatile memory before production startup; reset/scenario/theme/language changes reload a fresh session. Use immutable deployment URLs per manifest revision; refresh the iframe URL after an agent edit. Keep App and preview origins/storage separate. Do not place credentials, account snapshots, TURN servers, SDP or physical device IDs in fixtures.

## Message protocol 1.0

Direct iframe URL parameters: `scenario=typical|complex|failure`, `themeMode=light|dark`, `language=zh-CN|zh-TW|en`, `parentOrigin=<exact HTTP(S) parent origin>`, `instanceId=<caller session ID>`. URL parameters configure only preview. Without a parent origin it is standalone and accepts no parent controls.

Messages are `{protocol:'life-preview',version:'1.0',instanceId,type,payload}`. Parent commands: `configure` with optional `{scenario,theme,language}`, or `reset` (same options supported). Changes reload/reset the preview, rather than retaining stale pending callbacks/cache. Replies: `ready` with configuration (host/scripts initialized; list requests may still be loading), `operation` with a plugin ID/name or simulated-write route, and `error` with a message. Both ends must check origin, `event.source`, instance ID, protocol/version, and payload enums. Never use `'*'` target origins. Reported plugin acceptance is a simulated route acknowledgement, not real presentation.

## Maintained API fixtures

JSON fields: `schemaVersion:'1.0'`, scenario `id`, nested `spaces`, `devices`, `definitions`, `automations`, `scenes`, and optional route failure counts. IDs are synthetic `mock-*`; all space/device/definition/automation/trigger identities must match. Keep real response field names, device capability types, endpoints/functions/traits and the normal `code/data` envelope. API names are preserved; app-owned UI remains localized. Fixtures are permitted only under `preview/` and the skill's preview resources, never production assets.

Supported routes match those currently used by the page: GET spaces, paginated devices with `deviceName`, definitions with `deviceIds`, paginated automations with `automationName`, scenes with `pageNum/pageSize/needChildren` (plus legacy manual-trigger compatibility); POST typed trait writes/readback, automation status with success IDs, and sceneId/manual-pair execution acknowledgement. Unsupported routes/capabilities fail explicitly. Do not claim unsupported OpenAPI filters are simulated. Scene execution currently acknowledges an enabled known scene; it does not pretend arbitrary automation graphs ran or modify device states. Trait writes validate capability/type/range and update readback; automation writes update linked scene availability. Unknown IDs and read-only traits fail, and failed batches do not mutate partial state.

Scenarios: typical (21 devices, including HVAC), complex (240 devices/205 automations, long/XSS-like names, duplicate room labels, paging), failure (offline devices and recoverable read/write failures). Empty spaces and unassigned devices are included. Pure empty catalogs can be supplied by editing the scenario arrays with matching definitions/scenes. Validation checks identity/shape; it is not a full official OpenAPI schema validator. Future API revisions require maintaining both fixture contract and handler behavior.

Camera preview advertises no WebRTC preparation/session capability. A separately labeled sample image tests media framing only. The production camera runtime is unchanged, and preview never requests a camera, PeerConnection, native session or relay. Real camera LAN/remote media, Studio authentication, plugin presentation, actual device controls and supported WebView versions remain App/device verification gates.

Mine drawer preview: the isolated host accepts `openNavigationDrawer`, shows a labeled simulated modal and emits operation `{kind:"navigation-drawer"}`. No real account/profile settings or account requests are simulated. Closing restores focus and document scrolling; production uses only the advertised native host capability.

## Home AI assistant

Follow [home-ai-assistant-contract.md](home-ai-assistant-contract.md) for the below-overview entry, positive capability/space matching, zero additional request budget, optional native action and isolated preview operation.

The preview-only scenario studioHeader metadata simulates the native Studio name and local/cloud/error snapshot; prefix identities mock-. PreviewHost advertises the corresponding getter/subscription/unsubscription; App export contains none of these fixtures. Header status is separate from HTTP collection failure.

Favorite Home uses the same runtime renderer in canvas and App. Typical preview includes 24 physical devices / 25 endpoints with endpoint labels, a second channel, offline light, contact and lock.
