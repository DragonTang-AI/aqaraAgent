# Home AI assistant entry

## Presentation

By default place one AI entry immediately below the household overview, before notices/scenes/devices. An explicit `homeModuleOrder` overrides module position only; see `home-layout-contract.md`. The unscoped entry retains 问问 Aqara AI Agent / 問問 Aqara AI Agent / Ask Aqara AI Agent and its sparkle icon. For an explicit role, resolve the localized title, accessible opening label and static AI icon through the single `LifeI18n.aiPresentation(role)` mapping. Male uses a geometric status sparkle; female a soft four-point sparkle; senior a large clear star; child a playful three-star motif. These are role presentation variants, not device states or permissions. The child default omits the AI module, but an explicitly enabled child AI entry uses the child mapping. A custom theme changes paint and retains the chosen role's wording/icon; `roleSkin` alone does not rewrite content. Suggestion *wording* must additionally combine the role with the current Studio's confirmed room, device capability or environmental reading. Never use the old role-only generic questions, invent a room, claim someone is present, or imply a device can be controlled without an eligible model. Use the page's surface, border, action, text and radius tokens in light/dark themes. The reference screenshot's purple editor outline is not a runtime requirement. Keep one themed card container with a main entry button and separate suggestion buttons (44px minimum hit targets); never nest interactive elements. A bounded horizontal suggestion row supports long translations without widening the page. Clicking the main entry opens the native AI page without a question. Clicking a suggestion opens the same page and sends its currently displayed, localized text as the initial question, matching RN; suggestions are not H5 device writes.

When no suggestion has positive evidence, remove the row and use the compact card (about 60px). Keep this compact state during initial loading, cache-only display, confirmed empty catalogs or unavailable definitions. The entry itself remains available independently of Studio reads. Data-driven expansion must preserve page origin at the top and the existing semantic reading anchor when scrolled. Keep tab visibility, shared pull-refresh, card node identity and camera lifecycle unchanged.

## Device matching and bounded data reuse

Use normalized devices, exact public definitions and real space identities already obtained by the existing Home load and bounded overview index. `StudioRuntime.deriveAssistantHints(devices, spaces)` is a pure, single-pass projection; `overview.assistantHints.roomHints` carries deduplicated room IDs for confirmed models outside the visible page, alongside the backward-compatible Boolean facts. Resolve display names only from returned non-root spaces (or the explicit scoped room), never from device names or an unverified fallback. Ignore empty, excessive-length and control-character names. Do not add discovery requests, hidden cards, full-catalog scans or polling for the entry. A partial/failed catalog can supply positive evidence but cannot establish whole-home absence. Omit unconfirmed suggestions; recompute after refresh, room selection and language change, and never reuse cached facts as fresh evidence.

- Presence: a confirmed **online** device in that room has a readable Bool/Boolean trait with exact normalized code OccupancySensed, PresenceDetected, HumanPresence, Presence or Occupancy. A false or currently missing value still establishes capability. MotionDetected, names containing “人体”, and arbitrary strings do not. Ask whether that real room has someone; do not assert occupancy.
- Dimming: a confirmed online light in that room has a safe writable bounded brightness range (CurrentLevel, Brightness, BrightnessLevel or TargetBrightness). A switch-only or color-temperature-only light does not prove dimming. Mention that actual room; never hard-code 客厅.
- Environment: current valid ambient temperature **and** humidity readings exist in that same room, possibly from separate sensors. Apply the overview's independent-sensor exclusion of chip, motor and battery telemetry. Ask for the readings; do not label the room comfortable or safe from a threshold guess.
- Offline: at least one returned device in that room explicitly has normalized `online:false`. Ask about that room's offline devices; never assert that every device is disconnected.

At most three suggestion chips. Unscoped/male prioritize presence, dimming, offline, environment; female/senior/child prioritize environment, dimming, presence, offline. Prefer the currently selected room when eligible. Female prefers her confirmed rest/common-room ranking; senior and child **only** use their existing confirmed role-room ranks, preferring the explicit or unambiguous rest room, then relevant common rooms. No confirmed relevant room means no chip for that fact. Do not infer room ownership from role or create questions from mere role defaults. The visible text and native initial message must match exactly in zh-CN, zh-TW and en. Studio room names remain plain text data, never HTML. Definitions/space responses arriving later and models on later indexed pages can add proven suggestions without new entry-specific requests. Stored room IDs are transient projection facts, not account data or device identifiers; never persist question text or send it to a server from H5.

## Native enablement status

The AI section starts hidden, including its suggestion row, even when the generated Home configuration includes `aiAssistant`. `LifeBridge.subscribeUserAIAgentStatus(listener)` requires explicit host capability advertisement, attaches `UserAIAgentStatusUpdate` first, then invokes the native method once. The method responds with `{code:0,data:{status:boolean}}` and registers one listener for the current H5 view; repeated calls refresh the snapshot without duplicate native listeners. Native removes its listener when the H5 view is destroyed. Each event uses the same envelope and delivers a Boolean status. A push arriving before a method response wins over that older response. On DOM visibility recovery, native `PageVisibilityChanged` hidden-to-visible recovery, or native-context readiness, invoke the method again to reconcile missed changes. H5 removes its own event listener on `pagehide` and reattaches on a persisted `pageshow`.

Only `status:true` shows the entire AI section. Missing capability, failed invocation, malformed status, or `status:false` hides it without leaving a layout gap; when AI is configured as the first Home module, the next enabled module becomes the visual leader until AI is enabled again. Changes preserve the current reading anchor where possible. Keep this local feature switch separate from AI terms consent. Other dashboard variants without an AI entry do not need this status contract. The preview host simulates a known enabled state; old native hosts without the status capability fail closed.

When the user acts from a stale visible entry after native disablement, `openAIAssistant` returns `{code:0,data:{accepted:false,reason:"disabled",status:false}}` without navigation. H5 hides the entry and gives a localized off-state message. Native must check the switch immediately before routing; it must never report `accepted:true` for a disabled entry.

## Host action

`LifeBridge.openAIAssistant(content?)` sends `action:"openAIAssistant"` with unique onSuccess/onFailed callback names and optional flat `content` string. Trim strings; omitted/empty/whitespace content produces the original no-question payload. Reject non-string non-null arguments. Do not send URL, pageName, account/Studio ID or credentials. Require an explicit `openAIAssistant` advertisement and available transport, even for legacy empty lists. A nonempty question additionally requires the `aiAssistantInitialMessage` feature marker; it is not a callable method. Older hosts retain the plain entry; a question action shows localized update guidance and sends nothing rather than silently discarding the question or retrying it.

Require `{code:0,data:{accepted:true}}`; rejected/missing acknowledgements, failure callback and 8-second timeout fail. All AI buttons share one in-flight lock and disabled/aria-busy state, prevent duplicate navigation/questions across controls, and release on every settlement. Late suggestion rendering inherits the lock. Send the displayed question text using safe DOM text, including after language changes. Do not retry after ambiguous timeout: acceptance proves presentation only, not model completion or successful device execution.

The maintained iOS host advertises/registers the method, validates account epoch, reauthentication barrier and Studio/context lease, then executes on the main queue. A shared native router helper parses optional `params.content` through the same `aiAssistantPrompt` as RN OpenAIAssistantPage and forwards it to `LMAIAgentHost.present(initialMessage:)`, preserving native session/consent handling and its Bool acceptance result. Nonempty content starts a question after presentation; empty content just opens the page. The marker is advertised only by hosts with this forwarding implemented. Embedded H5 presents from its attached RN host; a standalone/pushed H5 presents from its visible controller, never a distant navigation root. The host acknowledgement proves acceptance only. AqaraLife Android advertises and handles the action; its status subscription is implemented in the dashboard H5 host. The iOS H5 status subscription is page-owned and separate from RN, shares the same switch source and change notification, returns the initial Boolean snapshot, deduplicates later events and releases its observer with the page. Both iOS WebView entries use the shared native-context capability/event list. iOS source integration still requires native build and real-host verification.

## Preview and verification

Only the isolated preview host advertises a simulated capability, opens a localized modal explicitly labeled simulated, and emits `operation:{kind:"ai-assistant",content?}` and displays the optional question as plain text in the simulated dialog. Close/Escape/backdrop restores the triggering control’s focus and scrolling. It does not send AI messages, control devices or load account data. Exclude all simulation from App exports.

Verify raw-definition matching (false/missing presence value, motion-only, unknown/read-only types, dimming vs switch/color-temperature, ambient readings from one or separate sensors, real room identity, offline and empty), initial and late overview evidence, role-room relevance, current-room switching, missing capabilities including legacy lists, accepted/rejected/error/timeout callbacks and cleanup on both H5 transports, duplicate cross-button clicks, exact localized content, whitespace omission, old-host marker gating, zero extra HTTP/device writes, localizations, themes, narrow screens, preview modal isolation, page origin and scrolled anchor stability. Existing runtime/tab/preview and portability gates remain required. Actual AI page presentation and consent/session behavior require user App build and device verification.

For an incremental AI-only edit to an existing favorite-mode product, run `smoke_test_h5.mjs <runtime> --native-entry-only` for both bridge transports, the AI smoke gate, and the AI/preview browser checks. The full `smoke_test_h5.mjs` cold-start fixtures assume space-mode Home and remain required on a freshly generated standard space-mode template; do not reinterpret favorite-mode deferred definitions as a regression.
