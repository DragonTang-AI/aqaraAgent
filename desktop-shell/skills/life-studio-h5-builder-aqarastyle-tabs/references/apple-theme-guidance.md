# Apple-inspired paint guidance

Read for Apple/iOS/Liquid Glass visual requests. Reviewed against Apple official guidance on 2026-10-14. This is a web adaptation, not a certified native Apple component implementation. The shared Aqara UI contract takes precedence whenever an Apple example would change card composition, dimensions, radii, spacing, typography, control geometry, camera framing or behavior. Do not copy native screenshots as a new layout.

## Materials and hierarchy

Apple separates navigation/control materials from content materials. Use the existing floating Tab as the main glass navigation layer; keep device cards and lists stable, readable content surfaces. Do not turn every card, AI entry and nested control into glass or stack multiple backdrop filters. For existing picker/detail sheets, adjust paint within the existing shared shell and its geometry; do not add nested glass planes.

Favor a regular-material-inspired Tab: restrained background blur, luminosity separation, a soft rim and a quiet selection fill. Clear glass is intended for visually rich media backgrounds; it is not the default for a text-heavy dashboard. Increasing transparency alone does not create convincing glass. Native refraction, automatic background-dependent appearance and system material variants are not provided by CSS blur; do not claim equivalence. These are web design decisions derived from [HIG Materials](https://developer.apple.com/design/human-interface-guidelines/materials).

## Color and creative freedom

Use neutral layered surfaces and reserve emphasis for actionable controls, selection and meaningful status. Let content remain prominent. Avoid coloring the background of every navigation item. Keep inactive navigation readable and the active icon/label distinguishable through the existing selected semantics. Apply this consistently to Home, Devices, Smart, AI/Mine entry and sheets.

The bundled Apple blue is a starting palette, not an Apple requirement. AI may choose another coherent accent or subtle warm/cool neutrals to fit the user's intent; retain semantic distinctions for on/off/offline, warnings and enabled automation. Use existing paint tokens for overview/scene gradients, text, borders and glass tint. These decisions follow [HIG Color](https://developer.apple.com/design/human-interface-guidelines/color); precise hex values are this Skill's web palette, not Apple's adaptive system colors.

For an Apple request, use `--style apple` for the bundled neutral/blue skin. If a distinct Apple-inspired palette is warranted, use the supported `--style custom --theme-tokens <file>` path with this guidance and `uiProfile: "aqara"`; do not silently ignore the chosen palette or introduce unsupported Apple runtime overrides. Tell the user it remains Apple-inspired despite the generator's custom skin identifier.

## Light and dark appearances

Design both palettes intentionally. In light mode, separate canvas, cards and floating layers through subtle tones, borders and restrained shadows. In dark mode, distinguish the dimmer base from the brighter elevated sheet/navigation surface; maintain readable primary/secondary labels without brightening every surface equally. Never use color inversion, a global dark overlay or whole-page opacity. Honor the existing native/preview theme source; switching appearance changes paint without new requests, rerendering controls or moving the page. The depth principle comes from [HIG Dark Mode](https://developer.apple.com/design/human-interface-guidelines/dark-mode); exact H5 token values remain configurable.

## Accessibility and web limits

Use text/icons and existing control states alongside color. Check small labels and icon edges over the actual composited glass background in both modes, including colorful content scrolling under the Tab. For this web adaptation, use WCAG contrast targets of 4.5:1 for normal readable text and 3:1 for large text and meaningful control boundaries; do not change the existing offline/disabled state contract to satisfy a decorative palette. Retain accessible names, keyboard focus and existing touch targets. These practical checks apply [HIG Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility).

Preserve existing no-backdrop-filter, reduced-transparency and reduced-motion fallbacks. Where the browser exposes increased contrast, keep labels and boundaries distinct using paint-only adjustments. Test only signals the web host actually supplies; do not invent native capabilities or claim CSS media queries receive every iOS accessibility preference. An unavailable signal must not leave the default interface unreadable. Apple also advises reviewing custom materials and avoiding overlapping glass controls in [Adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass).

## Focused review

For an Apple restyle, review light/dark Home, Devices and Smart, active/inactive Tab states, AI entry, off/offline cards, open picker/detail sheet and a narrow screen. Confirm the same S/M/L/XL measurements, title/status/control placement, 16:9 camera framing, gesture ownership and tab safe-area clearance as the Aqara baseline. Validate contrast under translucent layers and supported accessibility fallbacks. Use the existing theme/browser gates when changing presentation; keep QA outside deliveries.

Documentation-only reinforcement does not require regenerating artifacts or changing templates. Do not alter the Aqara visual contract, card selectors or native code to apply this guidance. Generation stays self-contained: official links provide provenance; a network connection, Apple SDK, external repository or another Skill is not required to use the summarized rules.

## Apple Home app requests

A request for the Apple Home / 家庭 app needs a more specific visual interpretation than generic Apple neutral/blue paint. Use a continuous restrained wallpaper-like background, light foreground headings over that background, quiet neutral tinted content surfaces, and a strong distinction between active bright accessory surfaces and inactive darker surfaces where the existing real state supports it. A generic green/gray canvas plus a dominant unrelated dark overview panel is not sufficient evidence of this style. Review the complete Home/Devices/Smart composition, not the Tab alone. A useful qualitative reference is [Apple’s Home redesign image](https://www.apple.com/newsroom/2022/06/apple-unveils-new-ways-to-share-and-communicate-in-ios-16/); that is a dated reference, not a claim that every current OS screen is identical.

Use the custom light/dark paint path when a wallpaper palette or state-specific material differs from the bundled Apple skin, and label it Apple Home inspired. Pure local CSS/vector wallpaper is permitted; do not bundle Apple screenshots as wallpaper, add raster dependencies, copy camera imagery, or require native frameworks. Keep the wallpaper as a noninteractive static background with no animation, polling, repeated blur filters or extra Studio reads. Keep small labels legible across the whole background and provide solid reduced-transparency surfaces. Make the two modes intentional rather than applying a dark overlay to the whole UI.

Foreground/on versus background/off paint follows existing `is-on`, `is-off`, `is-offline` and capability states only. Never infer a state for styling. A bright on-card can scope its existing semantic text/surface/action tokens for readable dark text; offline takes precedence and retains its documented 40% content, disabled writes and explicit label. Do not let an overlapping on-class leave dark text on an offline dark surface. Warm lighting emphasis is a paint choice, not a protocol/capability change. Keep overview content and layout, S/M/L/XL/Space-detail geometry, card placement, ranges, camera viewport and lifecycle unchanged. Let the overview share the wallpaper’s visual plane when appropriate instead of introducing a dominant dashboard-style hero. In preview, populate examples only through the real selector UI; never preset demo favorite IDs in App data.

For Apple Home card-palette refinement, prefer neutral luminous whites for proven on-states and neutral gray translucent inactive surfaces over a wallpaper; avoid letting every surface inherit a blue/green cast or a beige/gold wash. Category emphasis may distinguish lighting with restrained yellow, shades with cyan and climate with cool blue when actual types/capabilities support those controls. Keep the exact palette flexible, verify on/off/offline and dark appearance, and preserve thumb outlines/text contrast independently of a brighter slider fill. Color alone never substitutes for the existing state labels or controls.

Safe-area continuity is shared theme infrastructure: follow the continuous-background section of [theme-skin-contract.md](theme-skin-contract.md). At origin preserve the existing layered page background through the status area; use one shared neutral glass plane across status/header while scrolling, with continuous opacity and a feathered edge. Do not replace an approved Apple gradient or add a canvas-colored ring to the Smart segment.

## Reviewed spacing and light-card exception
The current shared H5 compact-light and Home-spacing rules in [aqara-visual-contract.md](aqara-visual-contract.md) supersede this document’s earlier “unchanged XL anatomy” wording. Use 32px module separation, 16px heading/vertical-card spacing, existing page margins and column widths. Replace all Home light L/XL cards with two-column M cards and explicit lazy Adjust sheets; retain real capabilities and all other card families. This applies across roles/themes, not only Apple paint. These values apply [HIG Layout](https://developer.apple.com/design/human-interface-guidelines/layout) grouping/alignment and [HIG Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility) comfortable controls; they are not a claimed Apple Home specification.
