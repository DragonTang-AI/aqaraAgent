# Senior and child daily-use dashboards

## Presentation and role intent

- Senior and child default `tabs:home`: no bottom Tab. Explicit tabs and prior user-confirmed combinations override; remove only inherited old senior Home/Devices defaults on role migration.
- Senior defaults restrained overview, Favorite scenes, Favorite devices, AI after primary controls, no Space-control batch module or pairing. Child defaults space devices, restrained overview and Favorite scenes, no AI/Space-control/pairing. Explicit choices can override; favorites and rich space devices remain mutually exclusive. Both retain disabled rich-card detail entry by default, existing inline controls and model-derived actions.
- For senior/child, Favorite scenes must precede the Home device module in generated HTML and config, whether devices use favorites or space mode. This also applies to module-order edits; reject an incompatible order before writing files.
- Senior recommendations concern daily rest, reading and night-time movement; child recommendations concern routines, reading/study and shared family activities. These are ranking directions, not a whitelist, an age-based permission system or proof of scene action content.
- Senior Home devices are at most three suitable real endpoints from the existing index. Child Home space cards first restrict actual rooms, then select at most four suitable real devices independently for each room. Do not invent devices to fill a count.
- Senior/child Home collections are automatic and isolated from official dashboard favorite settings. Always omit favoriteScenes/favoriteDevices from their metadata read plan, even when optional tabs are enabled. Do not consult official saved values or write, delete, migrate or synchronize them. Hide add controls before first paint; guard editor handlers and non-addable empty states. User room confirmation is a separate local preference, not a favorite write. Female/generic/male retain existing service-backed favorites.


## Real spaces and devices

Use actual IDs, hierarchy and names. New senior/female/child pages enable room recommendations through `roleRecommendations`; old pages without it keep their previous behavior. `--role-recommendations false` may restore generic room presentation; senior/child collection isolation and hidden editors remain mandatory. Explicit `--role-rest-space-id <real-ID>` wins, followed by a locally confirmed room (isolated by page path, metadata scope and role), exactly one dedicated senior/child room, then exactly one ordinary bedroom (exclude bedrooms explicitly named for the other role; do not classify role-named bathrooms/activity areas as bedrooms). Multiple eligible bedrooms/dedicated rooms require a compact inline choice; do not guess. No bedroom means recommendations only from actual common rooms. No fabricated room ownership.

Senior automatic device projection: wait for the existing bounded noncached capability index to settle (complete, partial or unavailable), then rank rest bedroom, living room, bathroom/corridor; prefer light, curtain, climate, then supported presence/contact sensors. At most three; exact favorite endpoint capability contracts still govern rendering/commands. Cache IDs per scope/index revision/room choice, patch live values into existing card nodes, and reuse the previous projection during same-scope refresh. Clear it on native identity change. Automatic projections do not require official favorite account scope; persist optional room preferences only with an available scope. Use a device-specific loading message; unavailable/partial failures terminate loading and show a localized retry state when no matches exist. A partial settled index may supply fewer valid matches; never force a full-home scan or leave a perpetual loader to fill three cards. A visible automatic favorite-device module keeps the shared bounded capability index enabled even when overview/AI are hidden. No separate startup resolve/reconciliation scan is introduced solely to rank recommendations. Female missing-key view defaults remain service-backed and use confirmed/unique ordinary bedroom, living room, dining/kitchen/study. Explicit female saved empty/list wins. Neither projection invents unsupported environmental favorite types.

Child Home space mode directly displays actual matched room chips (rest bedroom, living room and study spaces/descendants), defaulting to the resolved bedroom or first matched common room. No For you or synthetic recommendation/all-house chip. Within each room select up to four actual devices from verified device/endpoint types and available capabilities: everyday lighting, curtains, climate, then ambient temperature/humidity or presence sensing. Include an offline device when its actual type establishes suitability; keep its control disabled. Exclude cameras, locks, alarms, contact-only sensors, generic switches/outlets, media and hubs. A device name alone is insufficient proof of suitability. Prefer category diversity, then stable catalog order; fewer matches show fewer cards and no matches show a truthful empty state. Reuse the existing bounded overview capability index and locally loaded pages; never issue a request on a room switch or scan additional pages solely to fill four slots. Explicit Home scope/required-room constraints take precedence. `--role-recommendations false` restores generic room access. These are local presentation filters, not permission or discovery-query changes.

Physical-list type/name is only a candidate hint. Inspect exact endpoint capabilities before exposing a shortcut, slider, thermostat or speaker controls. Device-list online state is not power state. A generic Switch called a curtain, air-conditioner or video is not evidence of those capabilities. Cameras require actual camera/session capability evidence. Do not change the stable candidate/command contracts to force a recommendation. Device/scenes IDs and room mappings belong to task config, never reusable templates, examples copied from captures, or global role presets.

## Overview sources

Prefer two or three useful, supported metrics over fleet-management counts. Do not invent temperature/humidity, air quality, safety, occupancy, weather, schedules or fall detection. When supplied source data lacks suitable environmental sensors, generate a reduced supported `--overview-metrics` set (for example online) or omit the overview module if no useful metric remains. Do not create new metric IDs or relabel global statistics as role/room metrics. Adding favorite-only counts/lighting counts is a separate capability change, not a wording change.

`--overview-environment-space-id <real-ID>` independently chooses the source space and descendants for existing temperature/humidity aggregation; it never changes device discovery, Home filter state, favorites, presence scope or request budget. Resolve source names from the real tree and label readings accordingly. Without it, existing family/Home scope applies. Missing source or failed/invalid/no readings yields unavailable, with no whole-home fallback. Keep existing slots stable during loading/live data loss; do not hide rows after fetch and cause a layout jump. Source-specific labels reserve a bounded two-line area. The source is not inferred from the active room chip.

Exclude explicit chip/battery/motor/internal diagnostic readings. Exact TemperatureSensor + Temperature and HumiditySensor + RelativeHumidity endpoints identify independent environmental sensors; do not exclude these solely because a user-given device name contains internal/enclosure/box wording. For other endpoint types retain the internal-source exclusion. Never treat ColorTemperature or chip diagnostics as ambient readings. Reject null, empty, Boolean and nonfinite numeric values; preserve existing unit conversion/plausibility guards. Do not use raw list data as a reading. Source-specific aggregation reuses the existing definition/index reads. Senior/child default environmental metrics remain only when actual discovery can resolve valid data; runtime never invents substitutes. At generation with no reference catalog, keep truthful unavailable placeholders until discovery, without claiming a valid room source.

## Scene selection and isolation

Senior/child use `FavoriteScenes.automaticScenes(catalog, role)` over the existing shared real scene catalog, never official favorite settings. Senior priorities: night-time lighting, waking, sleep, reading, rest and home routines. Child: study, reading, waking, sleep, family play and home routines. Select only enabled role-relevant names/identities, deduplicate actual identity, cap at six, preserve stable catalog order within relevance buckets. Zero or fewer suitable candidates displays zero/fewer; never fill unrelated entries to reach six. Reject clearly named unlock/security/away/all-off/camera-recording actions from automatic suggestions. These conservative name hints are presentation recommendations, not proof that scene actions are safe or age-authorized. Never rename real scenes, synthesize controls, infer ownership or advertise parental authorization.

Both modules have no add/editor/selection persistence, including empty/loading/error states and keyboard/programmatic activation. Execute a displayed real scene through the existing exact endpoint with unchanged busy, success/failure and two-second feedback; request success is not a persistent lifestyle mode. Metadata failures or saved empty/list values do not affect automatic collections. Real scene catalog failures show a truthful unavailable state; keep layout slots stable.

Generic/male/female retain the existing first-use view-only defaults:1–6 all, >6 rank/fill six, saved records including explicit empty win, editable maximum10. Automatic senior/child mode takes precedence over these defaults and configured default IDs. Preview fixtures are isolated examples, never production device/scene IDs.
